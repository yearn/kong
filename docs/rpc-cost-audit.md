# RPC consumption audit

Audit date: 2026-10-28. Baseline: `73b0d7bd`. Scope: tracked application code, configuration, scripts, local git history, and installed viem/cache-manager implementations. Production request logs, billing exports, deployed environment, eRPC metrics/configuration, replica counts, and deployment/job history were not available. No production configuration, credentials, or backfill jobs were changed.

## Executive summary

The code confirms avoidable requests, but cannot establish which workload produced most of the invoice. Historical contract reads, timestamp resolution, and discovery scans are the largest plausible volume amplifiers. The four named networks account for 94.7% of the supplied seven-day RUs.

Implemented:

- Corrected an **11× block polling multiplier**: each per-chain job previously queried all 11 configured chains. Current jobs now query their own chain; old jobs without a chain retain their behavior.
- Prevented checkpoint loss when multiple workers finish the first log ranges for a contract concurrently. Lost ranges otherwise become eligible for another historical scan.
- Prevented scan planning from moving backwards before the requested start or into already covered nested ranges.
- Skipped decimals resolution for events with no amount to filter; retained stored zero decimals without falling through to RPC.
- Added opt-in, bounded RPC attempt metrics through the shared HTTP transport, including retries and job attribution.

At the checked-in schedule, the polling fix saves **9,504,000 JSON-RPC calls per 30 days across all 11 chains**. At 1 RU per call this is $95.04, conditional on all those calls being metered by Chainstack at the supplied marginal rate. For just the four named high-use networks it is $34.56. This is useful but far too small to explain the reported usage. Other fixes have input-dependent savings; no invented aggregate percentage is assigned to them.

Next: collect seven days of method/caller/retry metrics, reconcile them with provider exports, inspect historical job execution around October 16–23, and obtain capacity quotes for the four heavy networks. Prefer optimizing and negotiating the current service before a wholesale migration.

## Billing and normalization

The supplied invoice is $601.02 for 60,102,493 RUs: its rounded charge agrees with $0.00001/RU. The separate seven-day estimates total 153.25M RUs ($1,532.50). They cannot be assumed to cover the same billing interval. A flat 30-day extrapolation of that week is 656.786M RUs, or $6,567.86 at the supplied marginal rate; it is a scenario, not a forecast or a total including subscription charges.

Provider rules checked on the audit date:

- Chainstack Global Nodes classify relevant EVM methods by block age: recent reads cost 1 RU, historical reads at least 127 blocks behind cost 2. This applies to `eth_call`, headers, code and logs; logs use `fromBlock` when present. Archive Trader Nodes instead bill every request at 2 RUs. Debug/trace and `eth_callMany` have special treatment. JSON-RPC calls are counted individually, so an HTTP batch is not one billable call. Confirm each deployed node's type before assigning weights. [Chainstack RU rules](https://docs.chainstack.com/docs/request-units)
- The application's `FULL_NODE_DEPTH=400` is a routing heuristic, **not** a billing threshold. The `archive` metric label identifies an environment-variable route, not an RU classification. Do not issue extra head queries merely to estimate billing.
- On-chain Multicall3 aggregates multiple reads into one `eth_call` per calldata chunk. This can reduce billed calls. HTTP batching merely combines envelopes. viem 2.5.0 defaults multicall chunks to 1,024 calldata bytes (`node_modules/viem/actions/public/multicall.ts:131`), so a multicall invocation is not guaranteed to be one RPC.

### Failure, consumption and duplication rules for the inventory

**R (all direct sites):** installed viem `createTransport` defaults to three retries (four total attempts), 150ms exponential backoff and 10s HTTP timeout. `buildRequest.ts` honors numeric Retry-After, skips many permanent RPC errors, but retries HTTP 403/413 and RPC limit/internal errors. No second generic application RPC retry wrapper was found. BullMQ additions default to one attempt (`mq.ts:86`); a stalled/redelivered job, manual retry, or future fanout can execute again. Proxy retry multiplication is unknown. For independent retryable failure probability p, expected attempts with this budget are `1+p+p²+p³`; worst case 4. If a proxy independently permits k upstream attempts, the upper bound becomes 4k per logical call, not a measured factor.

Multicall uses aggregate3 through `readContract`/`call`; chunks execute with `Promise.allSettled`. `allowFailure` can turn a failed chunk or reverted member into per-member failures. Helpers either call `throwOnMulticallError`, propagate, or deliberately return undefined/default values. The metric outcome describes JSON-RPC success, not whether all inner calls succeeded. Oracle fallback, staking token capability probing, and decimals/asset fallback consume failed results as control flow; removing these blindly would change supported contracts.

All paths can duplicate across processes. BullMQ normally distributes a job to one consumer; replicas do not automatically duplicate every job. Explicit event and series job IDs deduplicate only while retained and only for identical payload keys. Snapshot fanout has no such ID. `findBusyMatch` is a non-atomic check, not a distributed lock. It includes waiting/prioritized/active work, not failed jobs; simultaneous fanouts can pass the check. The default worker concurrency scales 1→50 per queue per process at 200 queued jobs, sampled every 5s (`mq.ts:121`). Aggregate capacity scales with replicas, and each multicall can launch several HTTP operations. Pool sizes are currently one, so recycle behavior is dormant.

The only confirmed unused read was decimals resolution before testing whether an event has an amount. Base snapshots deliberately persist all zero-argument ABI fields, so a field lacking an obvious local reader is not enough evidence to remove it from an existing API contract.

### Historical completeness and caching

`fanout/events.ts:34` subtracts committed strides; `walklog` builds disjoint inclusive ranges. `load/index.ts:58` commits logs and completed range together, including empty successful scans. Failure before load commit leaves the range available for retry. Checkpoints survive restart; Redis queue/job retention does not replace them. Added seeding protects a new checkpoint row as well as an existing row. No ranges are marked complete on extraction failure. The log filter always supplies an address; event signatures normally narrow it further. If filtering produces an empty events array, installed viem emits an empty topic alternative; confirm provider behavior before treating that as a no-op or skipping the scan.

No adaptive oversized-range splitting exists. A limit failure may repeat the same oversized query up to four times, then leave a failed job until operational retry/cleanup. Splitting needs provider-error classification and range-completeness tests before adoption. Do not widen Polygon/Gnosis/Fantom limits based on Ethereum behavior.

The daily planner (`fanout/timeseries.ts:14`) queries missing days, treats stored null outputs as computed, and schedules the current day again. Explicit replay expands the date range. This is incremental, not an unconditional full-history replay. Failed hooks returning no output can remain missing and run again. Some historical scripts call `rpcs.up()` without `cache.up()`; in those processes `cache.wrap` simply runs the callback. Consequently every repeated timestamp search can hit RPC. Their dry-run flags can disable writes while still performing RPC.

Redis header keys include chain and height; no block hash or finality. A numbered unfinalized block is not immutable. Existing 24h numbered-header caching, 15min head pinning and strides reaching latest have reorg/freshness limitations: there is no automatic hash comparison/rollback in the extraction path. `latest_block` writes only move forward. This change does not lengthen TTLs, add historical state caching, alter reorg behavior, or claim those existing limitations are solved. A finality-aware rollback design is required before broadening caches. Creation search also currently advances its lower bound on any getCode error (`blocks.ts:122`), potentially confusing provider unavailability with absent bytecode; this pre-existing discovery correctness risk needs a fail-closed recovery change and historical fixtures, not a larger cache TTL. Cache-manager coalesces within a process; Redis shares stored values but does not provide a distributed in-flight lock. Web response/sparkline caching is downstream of indexing and does not itself cache `eth_call`.

No eRPC policy can be audited from this repository. Establish routing by comparing deployed endpoint configuration privately with proxy access logs, then measure upstream attempts, cache hit/miss, finality and per-method retry policies. Do not print endpoint URLs/tokens. A safe future state cache must include chain, to, calldata, from, value, overrides, complete block reference and canonical/finality policy; never reuse pending state or give latest a long historical TTL.

## Observability and operation

Enable `RPC_METRICS=true` with the existing `SENTRY_DSN` in a controlled rollout; this audit changes only the example environment, not production. Disabled clients retain the original transport. The wrapper emits `rpc.attempt` and `rpc.duration_ms_total` per actual transport attempt. SDK HTTP batching emits one observation per JSON-RPC member. Average attempt latency is duration sum / attempt count; retries / initial attempts gives retry amplification. These are counters, not latency percentiles.

Dimensions: chain ID; bounded method allowlist (other fallback); bounded `queue.job` name such as `fanout.timeseries` or `extract.timeseries` (unattributed outside workers); configured_archive/configured_full/chain_default provider route; success/error; retry boolean; log span bucket; `cache=unknown`. No address, calldata, URL, job ID, exact height/range or error-message labels. Provider identity is deliberately a route label, not guessed from credential-bearing URLs. Durations include SDK batch waiting. Observations are emitted when attempts settle; failures are attempted requests, not proof of a provider charge, and abrupt process termination can lose in-flight observations. Proxy retries/cache hits are not visible. Shared block-cache hits never enter this transport. The separate QA client is not covered.

Retry count is recoverable by aggregating `retry=true` attempt counts; there is no per-request identifier. Emission failure is swallowed and cannot replace an RPC result. `sentry.countMetric` now catches asynchronous metric-export failures too. Existing Sentry process initialization remains unchanged; compare emitted totals with provider exports and verify retention/aggregation settings before treating them as complete.

After deployment: confirm exactly one active repeatable per chain/schedule and inspect old root repeatables before removing duplicates. Expect `extract.block` caller attempt rate to drop from N²/30 to N/30 without reducing each chain's 30-second freshness. Compare chain freshness, missing-day counts, failed/stalled jobs, checkpoint gaps, retry rates and provider daily RUs for a full week. With multiple replicas, a process refreshes a chain's head only when it runs that chain's block job, so process-local latestBlocks may be missing or stale. A stale head would route blocks just past the real full-node depth to the full node, where pruned state reads can fail. Missing heads and heads not refreshed within 60 seconds therefore select archive. Check route mix as well as raw request counts, especially on fixed-price-class Trader endpoints. No DB migration or backfill is needed. The seed fix does not retroactively reconstruct lost ranges: normal gap planning discovers them; audit first rather than launching a bulk replay. Rollback is code-only; existing data/schema remains compatible.
