# Current allocator assignments

Kong #471 came from two factory-derived projections: `vault.allocator` selected the latest vault-bound deployment, while `allocator(chainId,vault).address` returned the factory's log address. A shared allocator deployment has governance as its second event argument and can serve many vaults. Neither factory event assigns a vault.

The V3 snapshot hook now materializes `allocatorState` from Envio `AddedNewVault`, `UpdateDebtAllocator`, `RemovedVault`, and vault `UpdateRoleManager` evidence. The shared resolver in `packages/lib/allocators.ts` orders events by block, transaction, log, and ID. It uses the authoritative manager, including assignments configured before a manager migration. It preserves any assigned address, including custom contracts and addresses without code. Zero is an explicit clear.

The projection pins the lower of Envio's processed block and the RPC finalized block. It requires indexing from block zero, normalized events version 3 or later, a configured source revision, matching manager/allocator RPC state, and a canonical assignment block hash. These are current-state checks, not certification of the complete allocation timeline. Required evidence failure produces an unavailable address and reason; a factory or prior allocator is never substituted.

Deployment records identify vault-bound versus shared interfaces. The shared factory is `0x03D43dF6FF894C848fC6F1A0a7E8a539Ef9A4C18`; its second argument is governance. The vault-bound factory is `0xFCf8c7C43DEdd567083B422D6770F23b78d15bDE`; it is configured for Ethereum and Base, not Katana. Factory addresses and family provenance are validated separately from assignments. Shared ratio reads take `(vault,strategy)`; vault-bound reads take `(strategy)`. Successful zero values stay zero. Unknown interfaces, no code, and failed reads retain the assigned address with unavailable configuration.

Both existing GraphQL paths read the same saved projection. `vault.allocatorState` and `allocator(...).state` disclose revision, block/hash, source revision, assignment ID, family and support. `Allocator.address` is now nullable so clearing and unavailable evidence do not invent an address. Targets and max ratios are derived from that same projection when the snapshot row is updated, including the stored composition. The snapshot row lock prevents delayed jobs from rolling the allocator revision backwards. REST's snapshot cache receives the same fields through its existing refresh process; normal REST HTTP/Redis cache freshness still applies, and consumers can compare the disclosed revision.

The hook also saves `allocatorLastAcceptedBlock` independently of `allocatorState`. Required evidence failures still clear the visible address and ratios, but cannot erase or advance that accepted block. Recovery must validate a projection at or above the last accepted block. Existing hooks initialize the guard from their saved validated projection on their next update; no backfill is needed.

## Adoption

This change depends on the normalization-v3 follow-up to [Envio PR #58](https://github.com/yearn/yearn-envio/pull/58), including initial/replacement arbitrary-address discovery and Base/Katana factory coverage. Its configured handlers and fixture tests do not prove production replay completeness. Validate each chain's replay, dynamic registrations after restart, and source revision before enabling it. No new Kong log scanner is added.

1. Deploy/replay the Envio follow-up for the chain, then set `ENVIO_ALLOCATION_GRAPHQL_URL`, its optional token, and `ENVIO_ALLOCATOR_SOURCE_REVISION` on Kong ingest. Configure archive RPCs for chains 1, 8453 and 747474. Do not copy credentials into review output.
2. From the Kong root, run a read-only projection check with `bun --env-file=.env packages/ingest/refresh-allocators.ts --chain=1 --vault=0xBe53A109B494E5c9f97b9Cd39Fe969BE68BF6204`. Omit `--vault` to check all stored V3 vaults on that chain. The command prints only identifiers, statuses and revisions.
3. After checking assignments/support and source coverage, repeat with `--write`. This updates the existing snapshot's allocator fields under its row lock and preserves concurrent accounting data. Repeat for Base and Katana. The regular snapshot hook subsequently keeps the projection current.
4. Run the existing REST vault/snapshot refresh (`packages/web/app/api/rest/refresh-vaults.cli.ts`) with the web service's environment. Check both GraphQL queries and the REST snapshot against the same assignment revision after cache refresh/expiry. Old factory-derived fields are suppressed until materialization, so run the refresh during the coordinated rollout.

Refresh output uses `outcome: "dry_run"` and `written: false` for a read-only candidate. With `--write`, the address, support, revision and block describe the committed projection. An accepted candidate reports `outcome: "applied"` and `written: true`; a candidate rejected by the block or observation-time guard reports the retained projection with `outcome: "skipped"` and `written: false`.

No database migration is needed. The current projection and its Envio inputs are saved together in `snapshot.hook.allocatorState`. Full historical normalized storage, immutable timeline runs, traces, DOA matching and chart APIs remain in the larger allocation-history milestone. Rollback requires reverting the ingest and web changes together and rebuilding snapshots/caches; doing so restores the known factory-derived behavior.

The deterministic tests cover Ethereum/Base/Katana shared replacement, vault-bound getters, custom/no-code addresses, zero clears, RPC and evidence failures, removal/migration, delayed writes, and agreement between the two GraphQL fields and snapshot projection. The Kong #471 transaction boundary is block `20,987,762`, transaction index `163`, log index `422`, transaction `0x3aa99e65b765359bb210eddaf0e9262ac3829e0a730c6f173d5073021d230b2d`; the exact log was verified through archive RPC. Tests use synthetic surrounding events and do not claim a full chain replay.

Local checks passed: 54 ingest mock tests, 88 web tests, two disposable Postgres allocator persistence tests, and the web production build. Refresh regressions cover applied/skipped/dry-run reporting and verify that persistence outcomes match the saved projection, including a rejected candidate with the same revision and block but an older observation time. Package lint checks use the same commands as CI. The ingest TypeScript check reports the same 17 pre-existing diagnostics (mock test typings and Vitest configuration) on this branch and on `origin/main`; no new diagnostic locations/codes were introduced. Live Envio replay/restart and production cache activation have not been performed.
